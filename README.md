# Assignment #3: Build an Agent Crew

## Let's Eat! — Agent Crew

## What game is this crew for?

**Let's Eat!** is a cozy deduction puzzle game for the web, built in Phaser 3. The player is a map assistant reading a group chat between six friends (Maya, Liam, Mina, Roxy, Cyrus and Brooke) and recommending the one restaurant that suits everyone's cravings, allergies, budget and vibe. The campaign has 20 levels across 4 chapters, each set in a different neighbourhood of a fictional city, and every pick earns 0–3 stars.

## What does the crew produce?

The crew produces the game's **content**, not its code. Everything it makes is a static file that the game loads at startup, so the finished game never calls an AI.

| Output | Made by | Used by |
| --- | --- | --- |
| `campaign_outline.json`: the plan for all 20 levels | Puzzle Architect | Every level build |
| `spec_level_XX.json`: each level's answer, decoys and rules | Puzzle Architect | Writer, Seeder, Validator |
| `dialogue_level_XX.json`: the group chat, with clue tags | Narrative Writer | ChatScene and the Notebook sidebar |
| `outcomes_level_XX.json`: reactions to every possible pick | Narrative Writer | OutcomeScene |
| `venues_level_XX.json` + `venue_registry_<district>.json`: restaurant cards and reviews | Map Seeder | ResultsListScene |
| `asset_manifest.json` + processed portraits and icons | Art Asset Agent | BootScene (preloading) |
| Validation, playtest and integration reports | Validator, Blind Playtester, Integration | The Orchestrator and Gabriella |
| `run_log.json` + `provenance_manifest.json` | Orchestrator, Provenance | Reviewing cost and who made what |

**Not produced by the crew:** the Phaser game code (built by Gabriella with Claude Code), music (hand-picked from Bensound and Pixabay) and source art (generated with prompts to NanoBanana and inspiration from Pintrest).

## Where each file goes
Drop this whole folder into the root of your game project (the folder you open Claude Code in).

| File | What it is | How Claude Code uses it |
| --- | --- | --- |
| `CLAUDE.md` | Orchestrator brief | Claude Code reads it automatically at the start of every session, so your main session *is* the Orchestrator |
| `.claude/agents/*.md` | Subagent briefs (Architect, Writer, Seeder, Playtester, Art) | Auto-detected as project subagents; see them with `/agents` |
| `docs/specs/*.md` | Specs for the Validator, Integration and Provenance scripts | Ask Claude Code to build each script from its spec |
| `docs/game_bible.md` | Centralized reference document for game world, lore, characters, tone, design rules | Replace with the Markdown export of the game bible doc |
| `content/levels/level_01/` | Gold-standard level 1 | Style reference for every agent |
| `content/registry/venue_registry_campus.json` | Starter venue registry | The Seeder reuses and extends it |
| `content/campaign/campaign_outline.json` | Outline template | The Architect fills all 20 rows |
| `logs/playtest_level_01_run1.example.json` | Example playtest report | Shows the Playtester's output format |

## First run, in order
1. Export the game bible doc as Markdown and save it over `docs/game_bible.md`.
2. Open Claude Code in the project folder and run `/agents` to confirm the five subagents appear.
3. Say: "Build scripts/validate.js and scripts/rules.json from docs/specs/validator.md."
4. Say: "Validate level_01." The gold level must pass. If it doesn't, fix the script or the rule, not the level.
5. Say: "Plan the campaign." Review and approve the outline.
6. Say: "Build level_02." Then repeat per level.

## What makes level 1 the gold standard
- First level handwriten to give the agent what good looks like; every level has a human-solvable solution
- 2 guests, 4 venues, stated clues: matches the chapter 1 row.
- One hard trap (Satay Spot: peanuts), two near misses (Noodle Cellar: no patio; Pizza Corner: wrong craving).
- Every decoy is a minimal pair of Noodle Nook: exactly one attribute differs.
- Every scoring constraint has a tagged chat line; reviews hint at tags without naming them.
- No budget limit here, since Maya isn't a guest; level 2 is a good place to introduce Maya and her budget.

## 3. What did the Critic agent catch?

The Critic runs after the Validator and before playtests. It reviews what a script can't check: voice, clue fairness, whether the reviews alone prove each trap, continuity and repetition. I ran it as an audit over the five approved chapter 1 levels.

| Level | Verdict | Must-fix | Suggestions |
| --- | --- | --- | --- |
| 01 | Pass | 0 | 3 |
| 02 | **Must fix** | **1** | 5 |
| 03 | Pass | 0 | 2 |
| 04 | Pass | 0 | 7 |
| 05 | Pass | 0 | 4 |

- **A continuity error that 6 playtest runs missed (level 02).** Cyrus says Maya is *"new to these lunches"*, but two lines later he says *"last time the three of us ate standing at a counter"*, and Maya confirms she was there. I fixed the line by hand.
- **A clue that points the wrong way (level 04).** Brooke asks for *"sandwiches"*, but no review confirms any venue serves them, and the only sandwich mentioned is the decoy's grilled cheese, so a careful player gets pulled toward a wrong answer. This led to a new Writer rule from level 06: no asks a review can't confirm.
- **Reused plot beats (level 05).** Mina's arc repeats level 03 almost beat for beat, and the puzzle is close to a re-skin of level 04 (same budget, same greasy near-miss, level 04's answer back as a decoy).
- **Smaller notes.** Telling venue names, a review that reads as written for the puzzle (*"don't come in craving a burger"*), a reaction mentioning "granola" that no review does, and one character voice slip (Cyrus's "pls").

The Critic was well calibrated: it found one real must-fix, never raised a rule that didn't yet apply above a suggestion, and didn't invent problems. After reviewing its output I made two calls of my own: portrait emotions in the bible are a guideline, not a rule per line, and a character's recurring phrasing is their voice, not repetition. Both are now in the Critic's brief.

# Assignment #5: Goal-Oriented Coding Agent

I built a goal-oriented feature agent for the game: `game/tools/feature-agent/` on the `game/prototype` branch. It works through a list of requirements taken from the game bible:

1. It finds the requirements the code doesn't meet yet.
2. It picks the most valuable one and has Claude Code write it.
3. It checks the result, then commits it.

It repeats this until every requirement is met. Before I built the agent, I used Claude Code in conversation to build a first set of features one at a time. Each section below covers the feature agent first, then those earlier features.

## How the feature agent works

1. **Requirements.** `requirements.json` holds 26 requirements. Each one quotes the bible and has:
   - a status taken from the bible (Locked, Proposed or Open)
   - an impact from 1 to 5, which I set
   - an effort score and its dependencies
   - a short spec, and detection rules
2. **Gap detection.** `scan()` checks each requirement's detection rules against the code: a file exists, a file contains a pattern, or a file no longer contains one. It uses no AI, so it's free and instant.
3. **Priority scoring.** `priority_score = (impact × status weight + 0.5 × missing features it unblocks) ÷ effort`. The status weights are Locked 2, Proposed 1 and Open 0.5. A requirement scores 0 while one of its dependencies is still missing.
4. **Code writing.** The top requirement's spec goes to Claude Code running headless (`claude -p`) inside `game/`. It can only use Read, Edit, Write, Glob and Grep, and has a spending cap per round.
5. **Checking and committing.** The round is kept only if all three checks pass:
   - only files in `game/` changed
   - the requirement is now detected
   - `npm run boot-test` passes

   A kept round is committed as `[feature_agent] <id>: <title>`. Otherwise the agent undoes it.
6. **Loop.** The agent rescans and repeats until nothing is missing.
   - If Claude's usage limit runs out mid-round, it undoes the half-finished work. It then either waits for the reset (`--resume-at`) or stops so I can rerun it later (`--on-limit stop`).
   - Every scan, score, write and check is logged in `feature_agent.log`.

## 2. Why did the agent pick these features?

### The feature agent

The order came from `priority_score`, and the log records every round's ranking. I set each feature's impact, and its status comes from the bible. Claude Code drafted the effort scores and dependencies, and I approved them. The agent's formula then decided the order:

1. **Credits file first (score 5.5).** The audio rules are Locked in the bible, the impact is 5, and two other missing features (the Credits screen and the music player) needed it.
2. **Credits screen (5) and the music player (3.5).** The player needed more work (effort 3), which lowered its score.
3. **Music on/off jumped to 10** as soon as the player existed: Locked, impact 5 and effort 1.

**Proposed features.**

4. Star totals (3.5): cheap, and the city map needed it.
5. Chapter cards, How to play and Reset progress, tied at 2.
6. City map and keyboard play (1).
7. Friends page last (0.33): an Open idea in the bible, impact 2 and effort 3.

**Review runs.**

8. Chapter card before How to play came first (4): impact 4, effort 1.
9. Then the muted slash (3), the `assets/` folders (2.5) and the friend card wording (2).
10. **The two small HUD runs.** Both change the same HUD so the second feature scored 0 until the first was in.

### Built with Claude Code in conversation (before the feature agent)

When first reading the assignment, I missed the part about the autonomous loop and added features through conversation with Claude. I asked for suggestions, and had Claude rank the ideas by working time to payout ratio. I ended up completing the whole list one at a time. Despite doing the assignment "wrong" the first time, I ended up with more features that helped polish the game (and would've eventually added anyways). It also helped me learn how tedious it felt and why the autonomous loop seems so streamlined - especially the part where we update the requirements.json instead of prompting the agent. This way there's a cleaner record of our wants list and it slightly saves on tokens.

These were the features added through conversation with Claude:

1. **Chat pacing and the clue recap** were its top picks: small changes to code that already existed, but they change how the game feels. The recap reuses the clue tags every chat line already has.
2. **Notebook stars** came from the Critic. I had the agent run the Critic on the new chat pacing, and it pointed out that the Notebook copied exactly the clue lines, which gave away implied clues.
3. **The Scrapbook and "Been here before"** use things the campaign already had: the bible's callbacks and the restaurants that come back in later levels. Both reward players who come back, which the bible says callbacks should do. Before building, the agent checked that levels 1–10 had enough of each to test with.
4. **The clue-depth check** turns a bible rule that nothing checked yet ("buried mid-conversation") into a cheap script that runs before the expensive agent steps.
5. **The Pipeline Health page** makes the agent crew's work visible. It also surfaced something I hadn't noticed: the critic raised only 1 must-fix across 19 rounds, and all the extra fix rounds came from suggestions I chose to act on.
6. **Sort/filter and accessibility** were on the original list for later chapters (chapter 4 has 7 restaurants per level) and to make the game easier to read and play.
